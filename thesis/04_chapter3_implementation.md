### 3.1.3 Реализация VU-воркера

Ключевой фрагмент реализации воркера приведён в листинге 3.2.

```python
def _vu_worker(benchmark, base_url, results, lock, stop_event):
    curl = pycurl.Curl()
    local_buffer = []
    while not stop_event.is_set():
        url = base_url + benchmark.url
        curl.setopt(pycurl.URL, url)
        t_start = time.time()
        try:
            curl.perform()
            success = curl.getinfo(pycurl.HTTP_CODE) < 400
        except pycurl.error:
            success = False
        latency_ms = (time.time() - t_start) * 1000
        local_buffer.append((latency_ms, time.time(), success))
        if len(local_buffer) >= 50:
            with lock:
                results.extend(local_buffer)
            local_buffer.clear()
    curl.close()
```

*Листинг 3.2 — Фрагмент реализации VU-воркера*

Каждый поток создаёт собственный экземпляр `pycurl.Curl()`, что обеспечивает независимость соединений между VU. Накопление в `local_buffer` с периодическим flush минимизирует время удержания `lock`.

### 3.1.4 Реализация профиля ramp_up

```python
class RampUpProfile(_BaseProfile):
    def run(self, benchmark, config, results):
        lock = threading.Lock()
        threads = []
        total_users = config.end_users - config.start_users
        interval = config.duration / max(total_users, 1)
        stop_events = []

        for _ in range(config.start_users):
            ev = threading.Event()
            t = threading.Thread(
                target=_vu_worker,
                args=(benchmark, config.base_url, results, lock, ev)
            )
            t.start()
            threads.append(t)
            stop_events.append(ev)

        t_start = time.time()
        added = 0
        while added < total_users:
            elapsed = time.time() - t_start
            target = int(elapsed / interval)
            while added < min(target, total_users):
                ev = threading.Event()
                t = threading.Thread(
                    target=_vu_worker,
                    args=(benchmark, config.base_url, results, lock, ev)
                )
                t.start()
                threads.append(t)
                stop_events.append(ev)
                added += 1
            time.sleep(0.1)

        time.sleep(max(0, config.duration - (time.time() - t_start)))
        for ev in stop_events:
            ev.set()
        for t in threads:
            t.join()
```

## 3.2 Реализация мониторинга

### 3.2.1 MetricsStore и TTL

`_MetricsStore` хранит последние значения метрик с временно́й меткой. При запросе `/metrics` значения старше TTL (15 секунд) отфильтровываются. Это решает проблему «протечки» метрик: если бенчмарк завершился, данные исчезают из Prometheus через 15 секунд, не смешиваясь с данными следующей фазы.

```python
class _MetricsStore:
    def __init__(self, ttl=15):
        self._data = {}
        self._ttl = ttl

    def update(self, key, value, labels=None):
        self._data[key] = {
            'value': value,
            'labels': labels or {},
            'ts': time.time()
        }

    def render(self):
        now = time.time()
        lines = []
        for key, entry in self._data.items():
            if now - entry['ts'] > self._ttl:
                continue
            label_str = ','.join(
                f'{k}="{v}"' for k, v in entry['labels'].items()
            )
            lines.append(f'{key}{{{label_str}}} {entry["value"]}')
        return '\n'.join(lines)
```

### 3.2.2 Стриминг метрик

Фоновый поток `_stream_metrics` выполняется каждые 5 секунд:

```python
def _stream_metrics(results, lock, store, stop_event):
    while not stop_event.is_set():
        time.sleep(5)
        now = time.time()
        window_start = now - 30  # скользящее окно 30 секунд
        with lock:
            recent = [(lat, ts, ok) for lat, ts, ok in results
                      if ts >= window_start]

        if not recent:
            continue

        latencies = [x[0] for x in recent]
        latencies.sort()
        n = len(latencies)

        p50 = latencies[int(n * 0.50)]
        p95 = latencies[int(n * 0.95)]
        p99 = latencies[int(n * 0.99)]

        # delta-RPS: запросы за последние 5 секунд
        delta_start = now - 5
        delta_count = sum(1 for _, ts, _ in recent if ts >= delta_start)
        rps = delta_count / 5.0

        store.update('perftest_rps', rps)
        store.update('perftest_latency_quantile_seconds', p50 / 1000,
                     {'quantile': 'p50'})
        store.update('perftest_latency_quantile_seconds', p95 / 1000,
                     {'quantile': 'p95'})
        store.update('perftest_latency_quantile_seconds', p99 / 1000,
                     {'quantile': 'p99'})
```

### 3.4.1 Профиль constant: базовая нагрузка

При постоянной нагрузке 5 VU Django-сервис работает стабильно: 191 983 запроса за 120 с при RPS 1 599,81 и нулевой частоте ошибок. Медиана латентности составила 2,966 мс, p99 — 7,053 мс. Профиль используется как точка отсчёта: именно его p99 (7 мс) служит базовым значением для оценки деградации в остальных профилях.

### 3.4.2 Профиль ramp_up: обнаружение точки насыщения

Профиль `ramp_up` (1 → 10 VU за 120 с) наглядно демонстрирует постепенный выход к точке насыщения. По завершении фазы средний RPS составил 1 581,57 req/s, p99 — 9,313 мс. Рост p99 по сравнению с `constant` (+32%) при незначительном снижении RPS (−1.1%) свидетельствует о приближении к пределу пропускной способности однопоточного Django dev-сервера. Скользящий график перцентилей в Grafana (рисунок 3.1) позволяет видеть этот рост в реальном времени.

### 3.4.3 Профиль spike: пиковая нагрузка

Профиль `spike` (base=3, peak=15 VU) наиболее показателен для демонстрации скользящего окна перцентилей. В момент скачка до 15 VU p99 возрастает до 38,586 мс (в **5,5 раза** относительно базового значения 7,053 мс). После возврата к базовому уровню VU p99 восстанавливается до значений, близких к `constant`, что хорошо видно на графике Grafana (рисунок 3.1).

Именно для этого профиля скользящее окно перцентилей принципиально: кумулятивные перцентили снижаются медленно — за несколько минут после спайка, создавая ложное впечатление продолжающейся деградации.

### 3.4.4 Профиль stepped: ступенчатый поиск порога

Профиль `stepped` (5 → 20 VU, 4 шага по 45 с) показал наибольшее накопление латентности в хвосте: p99 достигло 46,807 мс при среднем RPS 1 597,46 req/s. Горизонтальные плато на графике delta-RPS в Grafana соответствуют каждой ступени VU. На максимальной ступени (20 VU) ширина хвоста распределения значительно больше, чем у `ramp_up` при том же количестве VU — это объясняется большей суммарной нагрузкой (297 640 запросов за 180 с).

### 3.4.5 Профиль stress: выявление максимальной нагрузки

Профиль `stress` (1 → 20 VU, hold 90 с) зафиксировал максимальные значения латентности среди всех профилей: p95 = 38,344 мс, p99 = **69,044 мс**. Это в 9.8 раза превышает базовый p99 при `constant`. Фаза удержания 90 с при 20 VU позволила накопить значительную очередь запросов на стороне Django dev-сервера. Частота ошибок при этом оставалась нулевой — сервис под нагрузкой замедляется, но не отказывает.

### 3.4.6 Профиль soak: стабильность при длительной нагрузке

Профиль `soak` (4 VU, 120 с) продемонстрировал наилучшие показатели латентности: p50 = 2,345 мс, p99 = 6,022 мс — ниже, чем у `constant` (5 VU). При умеренной нагрузке 4 VU Django dev-сервер работает в недонасыщенном режиме, очередь запросов минимальна. Метрики не демонстрируют нарастающего тренда за период наблюдения. Для обнаружения утечек памяти в production-приложениях рекомендуется продолжительность soak от 30 минут до нескольких часов.

### 3.4.7 Верификация корректности метрик

Для верификации значений RPS и перцентилей использовались три независимых канала:

1. **Вывод в терминал** (`_print_progress`, каждые 400 мс): значения RPS и числа ошибок.
2. **Prometheus → Grafana**: значения p50/p95/p99 в реальном времени.
3. **HTML-отчёт**: итоговая таблица перцентилей и гистограммы за всю фазу.

Расхождение между терминальным RPS и delta-RPS в Prometheus не превысило 3% (объясняется различием временны́х окон: 400 мс vs 5 с). Значения перцентилей в Prometheus и HTML-отчёте совпали с точностью до округления (±1 мс), что подтверждает корректность реализации скользящего окна.

## 3.5 Решённые инженерные проблемы

### 3.5.1 Перцентили рисовались одной линией в Grafana

**Проблема:** p50, p95 и p99 совпадали визуально через несколько тысяч запросов.

**Причина:** кумулятивный расчёт — накопленные данные нивелируют различие между перцентилями через 2–3 тысячи запросов.

**Решение:** скользящее окно 30 секунд. Теперь при профиле `spike` p99 резко растёт и быстро снижается, тогда как p50 остаётся низким.

### 3.5.2 RPS не отражал форму паттерна

**Проблема:** на профиле `stepped` RPS менялся слишком плавно и не показывал ступени.

**Причина:** `total_requests / total_elapsed` — медленно меняющееся среднее.

**Решение:** `delta_requests_5s / 5` — быстро реагирует на изменение числа VU. Ступени `stepped` отчётливо видны как горизонтальные плато на графике.

### 3.5.3 Гистограмма вырождалась из-за выбросов

**Проблема:** при наличии единичных выбросов гистограмма латентности сжималась: 99% значений попадали в первый бакет, остальные были пусты.

**Причина:** диапазон бакетов по `max(latencies)` — один выброс 2000 мс при медиане 5 мс делал первый бакет «всем».

**Решение:** `max_bucket = p99 × 1,2`. 99% значений всегда попадают в видимую область гистограммы.

### 3.5.4 Grafana: пустой дашборд после рестарта

**Проблема:** после `docker-compose up` дашборд загружался без источника данных — все панели показывали «No data».

**Причина:** `"datasource": "${DS_PROMETHEUS}"` в `dashboard.json` — шаблонная переменная не разрешается при provisioning.

**Решение:** `"datasource": "Prometheus"` (строковый UID) + файл `grafana-dashboards.yml`. Дашборд загружается автоматически при `docker-compose up`.

### 3.5.5 Метрики появлялись только в конце фазы

**Проблема:** Grafana-дашборд оставался пустым на протяжении всей фазы и заполнялся только в самом конце.

**Причина:** VU-потоки сбрасывали буфер только при завершении, т.е. в конце фазы.

**Решение:** flush каждые 50 запросов. При 10 VU и латентности 5 мс данные обновляются каждые ~250 мс.

## 3.6 Оценка расширяемости системы

### 3.6.1 Добавление нового профиля нагрузки

Для добавления нового профиля нагрузки достаточно:

1) написать класс-наследник `_BaseProfile` (~20–30 строк);
2) зарегистрировать его в словаре `PROFILE_TYPES`.

Пример нового профиля `breakpoint` (автоматическая остановка при превышении error rate порогового значения) может быть реализован за ~30 строк кода без изменения остальных модулей.

### 3.6.2 Плагинная система

Плагин — обычный `.py`-файл, подключаемый через `--import_extensions`. Он расширяет словари `COMPARATORS`, `GENERATORS`, `EXTRACTORS`, `AGGREGATORS` — без fork репозитория и без правок ядра.

## 3.7 Выводы

Нагрузочный эксперимент подтвердил, что perftest справляется с задачей: 1 296 918 запросов, 0% ошибок, стабильный RPS на протяжении всех шести профилей. Точка насыщения Django dev-server — ~1 600 req/s — определяется архитектурой самого сервиса (однопоточный WSGI), а не генератором нагрузки.

Эксперимент также подтвердил ценность трёх ключевых инженерных решений. Скользящее окно: при spike-профиле p99 растёт с 7 мс до 39 мс и так же быстро падает — кумулятивные метрики этот пик размывают за несколько минут. Delta-RPS: ступени `stepped`-профиля на графике видны как горизонтальные плато, а не как плавная кривая. TTL-фильтрация: после завершения каждой фазы метрики исчезают из Prometheus сами, следующий профиль начинается с чистого листа.

Пять решённых инженерных проблем (скользящее окно, delta-RPS, обрезка гистограммы по p99 × 1,2, строковый UID источника данных Grafana и flush буфера каждые 50 запросов) не очевидны при проектировании, но каждая из них критична для читаемости мониторинга в реальном времени.
