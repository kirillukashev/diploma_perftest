# 1 Теоретические основы нагрузочного тестирования REST API

## 1.1 Понятие и виды нагрузочного тестирования

**1.1.1 Определение нагрузочного тестирования**

Нагрузочное тестирование (load testing) — вид нефункционального тестирования программного обеспечения, направленный на оценку поведения системы при спланированном увеличении числа одновременных пользователей или интенсивности запросов (IEEE Std 829, 2008). В отличие от функционального тестирования, проверяющего корректность ответов, нагрузочное тестирование исследует производительностные характеристики: пропускную способность, латентность, потребление ресурсов и устойчивость к отказам.

Нагрузочное тестирование применяется для:

– определения максимальной производительности системы (throughput capacity);
– выявления точки насыщения — уровня нагрузки, при котором деградация качества обслуживания становится недопустимой;
– обнаружения утечек ресурсов при длительной умеренной нагрузке;
– проверки устойчивости к кратковременным пиковым всплескам трафика;
– верификации соответствия нефункциональным требованиям (SLA/SLO).

**1.1.2 Виды нагрузочного тестирования**

В практике разработки принято выделять несколько разновидностей нагрузочного тестирования, отличающихся целью и характером нагрузки [14, 16].

*Таблица 1.1 — Виды нагрузочного тестирования*

| Вид | Характер нагрузки | Цель |
| --- | --- | --- |
| Load testing | Нарастающая или постоянная нагрузка до ожидаемого предела | Проверка поведения в штатных условиях |
| Stress testing | Нагрузка выше ожидаемого максимума | Поиск точки отказа и оценка восстановления |
| Spike testing | Резкий кратковременный всплеск нагрузки | Проверка устойчивости к флеш-мобам |
| Soak testing | Умеренная нагрузка в течение нескольких часов | Обнаружение утечек памяти и деградации |
| Volume testing | Большой объём данных | Оценка влияния размера данных на производительность |

**1.1.3 Метрики производительности**

Ключевые показатели нагрузочного тестирования делятся на показатели пропускной способности и показатели времени отклика (Menascé, Almeida, 2000).

**Пропускная способность (throughput)** измеряется в запросах в секунду (RPS, requests per second) или транзакциях в секунду (TPS). Для корректного отображения динамики используется дифференциальный подход: RPS вычисляется как число запросов за последний интервал времени (delta-RPS), а не как отношение суммарного числа запросов к общему времени теста.

**Латентность (latency)** — время от отправки запроса до получения ответа. Оценка только среднего значения неинформативна: среднее маскирует хвосты распределения, существенные для пользовательского опыта. Промышленным стандартом стал анализ перцентилей:

$$
p_k = \min\{x : F(x) \geq k/100\} \tag{1.1}
$$

где $F(x)$ — эмпирическая функция распределения латентностей. Для нагрузочного тестирования наиболее информативны p50 (медиана), p95 и p99 (Bezemer, Zaidman, 2019).

**Коэффициент ошибок (error rate)** — доля запросов, завершившихся с ошибкой (HTTP 5xx, таймаут, сетевой сбой).

## 1.2 Модели нагрузки и виртуальные пользователи

**1.2.1 Концепция виртуального пользователя**

Виртуальный пользователь (Virtual User, VU) — программный агент, имитирующий поведение одного реального пользователя системы. Каждый VU независимо генерирует запросы и ожидает ответов. Число одновременно активных VU определяет степень параллелизма нагрузки (Heusser, Leitner, 2012).

Модель открытой нагрузки (open workload) предполагает, что новые запросы поступают независимо от состояния сервера — прибытие описывается пуассоновским процессом с интенсивностью λ. Модель закрытой нагрузки (closed workload) предполагает фиксированное число VU: после получения ответа VU немедленно отправляет следующий запрос. Perftest реализует модель закрытой нагрузки: N VU генерируют непрерывный поток запросов.

**1.2.2 Профили нагрузки**

Профиль нагрузки описывает, как изменяется число VU или интенсивность запросов во времени. В индустрии устоялся ряд стандартных паттернов, реализованных, в частности, в k6, Gatling и Locust (Shkuro, 2019).

*Таблица 1.2 — Стандартные паттерны нагрузки*

| Паттерн | Форма N(t) | Назначение |
| --- | --- | --- |
| `constant` | Постоянный N | Проверка стабильности при базовой нагрузке |
| `ramp_up` | Линейный рост | Поиск порога деградации латентности |
| `spike` | Скачок и возврат | Устойчивость к внезапным пикам |
| `stepped` | Ступенчатый рост | Точное определение точки насыщения |
| `stress` | Рост → удержание → снижение | Максимальная ёмкость и восстановление |
| `soak` | Постоянный N, длительно | Утечки памяти, деградация соединений |

**1.2.3 Теория очередей применительно к нагрузочному тестированию**

Поведение веб-сервера под нагрузкой описывается моделью M/M/1 теории массового обслуживания (Kleinrock, 1975). При интенсивности поступления запросов λ и интенсивности обслуживания μ коэффициент загрузки сервера:

$$
\rho = \frac{\lambda}{\mu} \tag{1.2}
$$

При ρ < 1 очередь стабильна, среднее время ожидания в очереди:

$$
W_q = \frac{\rho}{\mu(1 - \rho)} \tag{1.3}
$$

При ρ → 1 время ожидания стремится к бесконечности — это и есть точка насыщения. Практически точка насыщения наблюдается как выход RPS на плато при дальнейшем росте числа VU при одновременном резком росте p95/p99.

## 1.3 Обзор существующих программных средств нагрузочного тестирования

**1.3.1 КИП (1С:Корпоративный инструментальный пакет)**

«1С:Корпоративный инструментальный пакет 8» (КИП) — программный продукт компании 1С, предназначенный для мониторинга, анализа производительности и нагрузочного тестирования информационных систем на платформе «1С:Предприятие 8» (1С, 2023). В состав КИП входят несколько подсистем; непосредственно нагрузочное тестирование обеспечивает **Тест-центр** — инструмент автоматизации многопользовательских нагрузочных испытаний.

Тест-центр моделирует работу предприятия без участия реальных пользователей: сценарии описывают бизнес-процессы 1С (создание документов, формирование отчётов). Производительность оценивается по методике APDEX с целевым временем 15 секунд на полный цикл операции; результат — максимальное число «условных пользователей 1С», при котором APDEX ≥ 0,85.

Ключевое ограничение: КИП Тест-центр не предназначен для тестирования произвольных REST API — он работает исключительно с приложениями на платформе «1С:Предприятие 8» через UI-сценарии. Для REST-сервисов платформы 1С:Предприятие Элемент, не использующих традиционный 1С-клиент, применимость КИП ограничена.

**1.3.2 Яндекс.Танк (Yandex.Tank)**

Яндекс.Танк — инструмент нагрузочного тестирования с открытым исходным кодом, разработанный компанией Яндекс. Поддерживает HTTP и другие протоколы, имеет плагинную архитектуру и возможность интеграции с внешними системами мониторинга через Graphite и InfluxDB. Основные ограничения: высокий порог входа, отсутствие простого декларативного формата для описания паттернов нагрузки, нет нативной интеграции с Prometheus (Yandex, 2023).

**1.3.3 Apache JMeter**

JMeter — зрелый инструмент нагрузочного тестирования на Java, разработанный Apache Foundation (Halili, 2008). Поддерживает широкий спектр протоколов (HTTP, JDBC, FTP, SOAP) и обладает графическим интерфейсом. Основные ограничения: высокое потребление памяти (каждый поток JVM требует ~1 МБ), сложность встраивания в CI/CD без GUI, отсутствие нативной интеграции с Prometheus.

**1.3.4 k6**

k6 — современный инструмент нагрузочного тестирования, написанный на Go с JavaScript API для описания сценариев (Shkuro, 2019). Отличается высокой эффективностью (тысячи VU на одном инстансе), встроенной интеграцией с Prometheus через remote write и поддержкой облачного исполнения. Ограничение — требование JavaScript для написания сценариев и Go для расширений.

**1.3.5 Locust**

Locust — Python-инструмент нагрузочного тестирования с описанием сценариев на Python (Heusser, Leitner, 2012). Поддерживает распределённый режим и имеет веб-интерфейс. Ограничения: сценарии пишутся на Python-коде, а не в декларативном формате; нет встроенных паттернов нагрузки с временным управлением.

**1.3.6 Gatling**

Gatling — инструмент нагрузочного тестирования на Scala с DSL для описания сценариев (Couteau, 2013). Асинхронная модель на Akka/Netty обеспечивает высокую производительность. Ограничения: высокий порог входа (Scala/JVM-экосистема), сложность встраивания в Python-проекты.

**1.3.7 PyRestTest**

PyRestTest — Python-инструмент, основанный на декларативном YAML-формате для описания функциональных HTTP-тестов (Bhatt, 2014). Поддерживает валидаторы, привязки переменных и экстракторы. Ограничения: отсутствие профилей нагрузки, нет поддержки Prometheus/Grafana, проект не развивается с 2017 года.

**1.3.8 Сравнительный анализ**

*Таблица 1.3 — Сравнение программных средств нагрузочного тестирования*

| Критерий | КИП (1С) | Яндекс.Танк | JMeter | k6 | Locust | perftest |
| --- | --- | --- | --- | --- | --- | --- |
| Поддержка REST API | Только 1С-сервисы | ✓ | ✓ | ✓ | ✓ | ✓ |
| Язык сценариев | GUI/1С бизнес-процессы | YAML/INI | XML/GUI | JavaScript | Python | **YAML** |
| Профили нагрузки | Автоинкремент VU | Частично | Через плагин | 5 типов | Частично | **6 типов** |
| Метрика качества | APDEX (15 с) | Перцентили | Перцентили | Перцентили | Перцентили | **p50/p95/p99** |
| Встроенный Prometheus | Нет | Нет | Нет | Remote write | Нет | **Нативный** |
| HTML-отчёты | Нет | Нет | Да | Да | Частично | **Да** |
| Декларативный YAML | Нет | Частично | Нет | Нет | Нет | **Да** |
| Порог входа | Высокий | Высокий | Высокий | Средний | Низкий | **Низкий** |
| Язык ядра | 1С/Java | Python/Go | Java | Go | Python | Python |

Из сравнения следует, что разработанный программный продукт perftest занимает нишу Python-средства с YAML-декларативным подходом, шестью встроенными паттернами нагрузки и нативной интеграцией с Prometheus/Grafana — сочетанием характеристик, которое не реализовано ни одним из рассмотренных аналогов (см. таблицу 1.3). В отличие от КИП Тест-центра, perftest не привязан к конкретной платформе и применим для тестирования любых HTTP REST-сервисов, включая сервисы 1С:Предприятие Элемент.

## 1.4 REST API как объект нагрузочного тестирования

**1.4.1 Архитектурный стиль REST**

REST (Representational State Transfer) — архитектурный стиль распределённых гипермедийных систем, сформулированный Fielding (2000). Ключевые ограничения REST: stateless, единый интерфейс (HTTP-методы GET/POST/PUT/PATCH/DELETE), ресурсно-ориентированный подход, кешируемость ответов.

Нагрузочное тестирование REST API имеет специфические особенности по сравнению с тестированием традиционных сервисов:

– каждый эндпоинт имеет самостоятельный профиль производительности;
– latency включает сетевой оверхед, TLS-рукопожатие, сериализацию/десериализацию JSON;
– корректность ответов верифицируется параллельно с измерением производительности.

**1.4.2 HTTP-клиенты для генерации нагрузки**

Выбор HTTP-клиента существенно влияет на эффективность инструмента нагрузочного тестирования. pycurl (Python-обёртка над libcurl) — предпочтительный выбор по ряду причин: libcurl реализована на C и имеет минимальный overhead при выполнении HTTP-запросов; pycurl освобождает GIL (Global Interpreter Lock) на время сетевого ожидания, что позволяет потокам Python работать параллельно при I/O-bound нагрузке; pycurl поддерживает HTTP/1.1, HTTP/2, HTTPS, keep-alive и другие промышленные стандарты (Stenberg, 2004).

## 1.5 Мониторинг и наблюдаемость

**1.5.1 Prometheus и модель метрик**

Prometheus — система мониторинга с открытым исходным кодом, использующая модель pull: сервер периодически опрашивает эндпоинты `/metrics` целевых сервисов (Volz, 2016). Метрики в формате Prometheus exposition format — имя, лейблы, значение, временна́я метка. Лейблы вместо отдельных имён метрик — стандарт Prometheus:

```
perftest_latency_quantile_seconds{quantile="p95", benchmark="..."} 0.042
```

Это даёт возможность фильтровать и агрегировать данные через PromQL без изменения инструментированного кода.

**1.5.2 Grafana и визуализация**

Grafana — платформа для визуализации метрик из различных источников данных. Provisioning через YAML/JSON позволяет воспроизводить конфигурацию дашборда автоматически при запуске контейнера без ручного импорта через UI (Grafana Labs, 2023).

## 1.6 Выводы

Нагрузочное тестирование REST API отличается от тестирования монолитов: каждый эндпоинт имеет собственный профиль производительности, а метрики нужны в реальном времени — не после окончания теста. Перцентили распределения латентности (p50, p95, p99) предпочтительнее среднего, потому что хвост распределения напрямую влияет на пользовательский опыт.

Из семи рассмотренных средств ни одно не закрывает одновременно три требования: декларативный YAML, именованные паттерны нагрузки и нативный Prometheus. КИП Тест-центр решает другую задачу — автоматизацию нагрузочных испытаний в экосистеме 1С:Предприятие 8 — и к тестированию произвольных REST-сервисов неприменим. Яндекс.Танк закрывает сценарии с высокой нагрузкой, но требует ручной настройки паттернов. JMeter, Locust, k6 и Gatling хорошо известны и мощны, однако требуют либо отдельного языка (Scala, JavaScript), либо программного кода для нестандартных паттернов. PyRestTest ближе всего по формату, но лишён поддержки нагрузочных профилей.

Выбор pycurl как HTTP-клиента обоснован: libcurl освобождает GIL на время I/O, что позволяет N потокам Python работать истинно параллельно при сетевом ожидании. Prometheus pull-модель и Grafana provisioning через JSON обеспечивают воспроизводимый мониторинговый стенд без ручной настройки UI.
