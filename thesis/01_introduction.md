# Введение

Веб-сервисы и REST API стали стандартным способом интеграции компонентов — и именно они чаще всего оказываются узким местом при росте трафика. Аварии из-за неожиданных пиков нагрузки обходятся дорого: по отраслевым оценкам, час простоя крупного сервиса — это сотни тысяч долларов [22]. Нагрузочное тестирование позволяет найти это узкое место до того, как его найдут пользователи.

**Актуальность.** Переход к микросервисной архитектуре усилил потребность в инструментах, заточенных именно под HTTP-эндпоинты: они должны генерировать конкретные паттерны нагрузки, проверять корректность ответов и отдавать метрики в реальном времени. Зрелые решения — JMeter, k6, Gatling, Locust — эту потребность закрывают, но каждое требует либо отдельного языка (JavaScript для k6, Scala для Gatling), либо XML-конфигурации, что повышает порог входа для Python-команд. Отечественный КИП 1С работает только с 1С:Предприятие 8, Яндекс.Танк не предоставляет простого декларативного формата для паттернов нагрузки. В итоге для REST-сервисов на Python — в том числе сервисов платформы 1С:Предприятие Элемент — удобного решения в открытом доступе нет.

**Степень разработанности темы.** Статистические модели веб-нагрузки заложены в работах Arlitt и Williamson [4]; аналитические модели производительности на основе теории очередей — у Menascé и Almeida [15]. Нагрузочное тестирование микросервисов рассмотрено в [9]. Сами программные средства — JMeter [11], Locust [12], k6 [17], Gatling [7] — хорошо описаны, сравнение их ограничений выполнено в [5]. Вместе с тем детальных описаний инженерных решений, обеспечивающих корректность метрик при потоковой нагрузке с переменным числом VU (скользящие окна, delta-RPS), в открытых источниках не встречается.

**Цель работы** — разработать программное средство нагрузочного тестирования REST-сервисов на Python с декларативным YAML-форматом, шестью паттернами нагрузки и интеграцией с Prometheus/Grafana, после чего экспериментально верифицировать его работу на тестовом сервисе.

**Критерии достижения цели:** тесты запускаются по YAML-файлу без написания кода; все шесть паттернов реализованы и верифицированы; система находит точку насыщения сервиса; числа RPS, перцентилей и error rate совпадают между тремя независимыми каналами вывода.

**Задачи:**

1. Провести обзор существующих программных средств нагрузочного тестирования и сформулировать требования к разрабатываемому продукту.
2. Спроектировать архитектуру: уровни YAML-конфигурации, ядра, мониторинга и отчётности.
3. Разработать потоковую модель виртуальных пользователей на основе pycurl.
4. Реализовать шесть паттернов нагрузки с единой иерархией классов.
5. Реализовать Prometheus-экспортер с TTL и скользящим окном перцентилей.
6. Разработать HTML-генератор отчётов с гистограммами латентности.
7. Развернуть тестовый REST-сервис и провести нагрузочные эксперименты.
8. Верифицировать метрики через три независимых канала и зафиксировать решённые инженерные проблемы.

Работа имеет как практическую, так и теоретическую ценность. В практическом плане: готовый продукт с открытым кодом, встраиваемый в CI/CD. В теоретическом: детальное описание инженерных решений для корректного отображения метрик при динамической нагрузке: скользящее окно для перцентилей, delta-RPS, TTL-фильтрация экспортёра.

**Методы исследования:** системный анализ и объектно-ориентированное проектирование при разработке архитектуры; нагрузочный эксперимент с контролируемым стендом (Django + SQLite in-memory) при верификации; статистический анализ перцентилей распределения латентности.

**Научная новизна:**

1. Предложен и реализован расчёт перцентилей латентности по скользящему окну (30 с) вместо кумулятивного. При профиле spike кумулятивные перцентили снижаются несколько минут после спайка — скользящее окно отражает ситуацию немедленно.
2. Введён delta-RPS — число запросов за последние 5 с, а не среднее за весь тест. Без delta-RPS ступенчатый профиль `stepped` на графике выглядит как плавная кривая.
3. Разработан Prometheus-экспортер с TTL-фильтрацией (15 с), изолирующий метрики соседних фаз: данные предыдущего бенчмарка исчезают из Prometheus сами, без ручных действий.
