# Заключение

Поставленная цель достигнута: разработан и верифицирован программный продукт **perftest** для нагрузочного тестирования REST-сервисов.

Сравнительный анализ семи существующих средств — КИП 1С, Яндекс.Танк, JMeter, k6, Gatling, Locust, PyRestTest — показал, что ни одно из них не сочетает одновременно декларативный YAML без написания кода, именованные паттерны нагрузки как первоклассную сущность и нативный экспорт в Prometheus. КИП Тест-центр решает другую задачу — автоматизацию бизнес-процессов 1С:Предприятие 8; к произвольным HTTP REST-сервисам он неприменим.

Реализованы четыре архитектурных уровня: YAML-конфигурация, ядро (парсинг, пул VU-потоков на pycurl, агрегация метрик), Prometheus-экспортер с TTL-фильтрацией и HTML-генератор отчётов. Шесть паттернов нагрузки (`constant`, `ramp_up`, `spike`, `stepped`, `stress`, `soak`) объединены единой иерархией классов и общим YAML-синтаксисом.

В ходе экспериментального прогона на тестовом Django-сервисе отправлено **1 296 918 запросов**, частота ошибок — 0%, средний RPS — 1 601,8 req/s. Сервер с однопоточным WSGI уходит в насыщение при ≈10–15 VU, что соответствует теоретической оценке 1/0,6 мс ≈ 1 666 req/s. Spike-профиль увеличивает p99 с 7,1 мс до 38,6 мс; stress-профиль — до 69,0 мс. Метрики сошлись между терминальным выводом, Prometheus/Grafana и HTML-отчётом.

В процессе разработки потребовалось решить пять нетривиальных инженерных проблем:

– кумулятивные перцентили скрывают динамику латентности при смене фазы → заменены скользящим окном 30 с;
– накопленный RPS не отражает форму паттерна → введён delta-RPS за последние 5 с;
– выброс в гистограмме латентности вырождал первый бакет → максимум бакетов ограничен p99 × 1,2;
– шаблонная переменная datasource ломала provisioning Grafana → заменена строковым UID;
– VU сбрасывали буфер только при завершении → добавлен flush каждые 50 запросов.

Продукт опубликован в открытом доступе и пригоден для встраивания в CI/CD пайплайн.

**Направления дальнейшей работы:**

1. Переход с threading на asyncio/aiohttp снимет ограничение GIL и позволит поднять число VU на порядок без роста числа потоков.
2. Профиль `breakpoint` с автоматической остановкой при превышении порога error rate избавит от ручного мониторинга при поиске точки отказа.
3. Распределённый режим с несколькими агентами нужен там, где один хост не может создать достаточную нагрузку.
4. Сравнение двух прогонов в HTML-отчёте превратит perftest в инструмент регрессионного анализа производительности.
5. Импорт HAR-файлов и OpenAPI-спецификаций позволит автоматически генерировать YAML-сценарии из реального трафика.
